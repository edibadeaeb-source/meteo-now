# METEO NOW security hardening — 2026.10.10.1

## Status and scope

This is an initial application hardening pass, not a comprehensive penetration test or a guarantee against attacks. No destructive production probes, notification broadcasts, production overload tests or database writes were performed during the audit.

Read-only production checks confirmed that `/app.py`, `/.git/HEAD` and `/requirements.txt` were publicly served. `/keys.py` was 404; no successful download of private server keys was observed. Firebase shallow queries to `push_subs`, `push_android_status` and `widget_cities_e2e` returned 200 without authentication. Payloads, subscription IDs, coordinates and keys were not printed or saved in the audit.

**Update, 2026-10-11: private mobile-data access has been deployed.** Both Render services now authenticate privately, and anonymous access to the database root, notification records and encrypted widget synchronization is denied. Explicit station paths retain temporary public writes for device compatibility. See [SECURITY-FIREBASE-20261011.md](SECURITY-FIREBASE-20261011.md) for deployed rules, verification and remaining work. The audit observations above describe the original state.

## Implemented protections

- Static responses use an explicit public-file allowlist. Python source, Git metadata, configuration, database files, exports, tests, documentation, hidden files and traversal paths are excluded. Public weather assets and Android Digital Asset Links remain available. Flask's default static route is disabled.
- Removed the OpenWeather key and direct-key fallback from public HTML. HTTP proxy failures return generic errors rather than exception URLs that could contain `appid`. A key previously exposed in public source must still be rotated in the provider account and server configuration; removal cannot invalidate existing copies or Git history.
- CORS allows the production app and configured additional HTTPS origins. Untrusted browser Origins and cross-site API requests are rejected. Native clients without Origin remain compatible. CORS is not an authentication mechanism and does not stop direct scripts.
- Request bodies are limited to 192 KiB. AI question, location, context, snapshot and history types/sizes are validated before calling the paid provider. At most 16 recent messages, each 4000 characters, are forwarded; complete conversations remain saved locally.
- SQLite quotas are shared across the two Gunicorn worker processes on the current single host. Default AI limits are 6 requests/minute and 30/day per IP, 20/minute and 200/day globally, plus at most two simultaneous AI requests. Global AI daily cap is configurable with `METEO_AI_DAILY_REQUESTS`. Failed attempts can consume request quota; this is a request-count ceiling, not an exact currency budget. IPv6 addresses within a /64 share a quota.
- General APIs allow 240 requests/minute/IP, 1200/minute globally. Tiles use separate, higher limits; climate, subscription and widget writes have additional limits. Rejections return 429 and Retry-After. Provider/network/database failures do not silently disable paid-AI protections.
- Render edge client headers are trusted only when `PORT` and `RENDER=true` identify the hosted Render environment. Arbitrary leftmost X-Forwarded-For values are not used. Direct self-hosting needs explicit proxy review.
- Cron authorization rejects missing/example secrets, uses constant-time comparisons and accepts Bearer or X-Cron-Secret headers. Existing query-secret jobs remain compatible; migrate them to headers and rotate the secret. Existing secrets of at least 16 characters remain accepted; choose a fresh random secret of at least 32 characters.
- Hosted sensor export/write routes require `METEO_ADMIN_TOKEN` in an Authorization Bearer header, at least 24 characters. Direct loopback development remains usable. Public legacy dashboard export buttons now require an administrative client; this does not affect mobile weather screens.
- Push endpoints must use supported HTTPS push-provider hosts, preventing arbitrary-host/private-network requests. New subscription keys have bounded valid encodings. Existing subscription updates and deletions require matching subscriber keys. The app now includes those keys when unsubscribing. These proofs remain vulnerable while Firebase itself publicly exposes the records; closing database access is mandatory.
- City names, search results and map labels are HTML-escaped; alert log and AI text remain plain text. HTML-to-text parsing uses an inert document. Browser tests cover malicious city and AI text.
- Added compatible CSP, anti-framing, no-sniff, referrer, permissions and HTTPS headers. CSP still permits legacy inline scripts/styles and broad HTTPS data/image providers; it is not a strict nonce-based XSS defense. A later interface refactor should remove inline handlers and tighten provider lists.
- Sensitive responses are not cached. API credential/service-account/private-key/database filenames are excluded from Git.
- Added server-only Firebase OAuth credentials via `FIREBASE_SERVICE_ACCOUNT_JSON` or `GOOGLE_APPLICATION_CREDENTIALS`; tokens refresh under a process lock and are sent as Authorization headers. `METEO_FIREBASE_REQUIRE_AUTH=1` fails closed if credentials are missing. Without configuration, migration compatibility preserves the existing backend behavior and does not protect the database by itself.

## Original migration plan — superseded by the 2026-10-11 deployment report

1. Export the current Firebase data and current security rules to private backups. Review the actual existing rules and device write paths; a restrictive child rule cannot revoke a parent `.read: true` or `.write: true` grant.
2. Create/use a dedicated server service account with the minimum required Realtime Database privileges. Keep its JSON private. Configure `FIREBASE_SERVICE_ACCOUNT_JSON` as a **secret environment variable in Render**, then set `METEO_FIREBASE_REQUIRE_AUTH=1`. Never paste the JSON into chat, Git, public static folders or frontend code.
3. Redeploy and verify authenticated server database reads/writes. Configure equivalent private authentication for ESP32/MQTT/LoRaWAN writers before revoking their anonymous writes. Mobile widget and permission sync already goes through the server; public weather sensor reads are distinct from user notification data.
4. Review `firebase/database.rules.proposed.json` against the backed-up rules. This stricter proposal denies anonymous station writes and remains unapplied. The deployed compatibility rules are now recorded separately in `firebase/database.rules.json`; see the new report before making further changes.
5. Apply reviewed rules only after the authenticated server and sensor writers work. Verify unauthenticated shallow GETs to private branches and root fail with 401/403, public weather reads still work, and a real phone can enable/disable notifications and synchronize widgets. Use local emulator tests for attempted writes; do not overwrite production records as a probe.
6. Rotate exposed OpenWeather credentials and any credentials discovered in the former public repository/source routes. Update Render and local private configuration before invalidating old credentials, verify normal weather requests, then revoke old keys. Review provider usage and billing for unexpected activity.

## Operational limits and next steps

- Temporary SQLite counters survive worker restarts on one filesystem but reset on container replacement/redeploy. They do not coordinate multiple service instances. Before scaling out, migrate rate limits/leases to shared Redis or equivalent storage. Configure provider-side spend limits separately; distributed bots can exhaust anonymous quotas even though they cannot bypass the global ceiling on a single running host.
- The platform's edge DDoS filtering complements these application limits; it does not replace authentication, database rules, monitoring or recovery plans.
- Enable 2FA for Firebase/Google, Render and GitHub; keep recovery codes and signing-key backups private. Review project membership and revoke unused access. These account changes were not performed.
- Add monitored alerts for abnormal AI usage, repeated 429/5xx and provider failures. No recurring monitoring automation was created.
- Dependency audit resolved 36 packages with no known advisories at audit time. This audits the resolver output, not an inventory of the already running Render container or a promise that packages have no unknown flaws. Frontend CDN dependencies remain a separate supply-chain review; self-hosting/pinning and strict CSP are follow-up work.

- Browser checks with actual Flask security headers passed for mobile startup, forecast, UV, city picker, AI, fonts and weather media. Injected HTML in city names and AI responses remained text and did not execute.
